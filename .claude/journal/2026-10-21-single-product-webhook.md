# One Product hook instead of three per-operation hooks

**Symptom:** the inbound product sync registered up to three separate Moloni hooks for the `Product` model (`stockChanged`, `create`, `update`). The receiver (`src/WebHooks/Products.php::products()`) always fetched the Moloni product before checking the operation, and the `switch` only had cases for those three operations.

**Cause / change:** a hook registered with no `operation` fires for every operation of its model, and the delivered payload still carries the real operation (`{companyId, model, operation, productId}`). So one hook can replace the three. `WebHooks::createHook()` now takes an optional `$operation` (default `null`) and omits the `operation` key from the mutation variables when not given — `Plugin::reinstallWebhooks()` and `Plugin::saveAutomations()` now install a single `createHook('Product')` when either `hook_stock_sync` or `hook_product_sync` is on. `WebHooks::deleteHooks()` cleans up the pre-existing per-operation hooks on resave — but only after two fixes in this PR: the URL filter was sent as `data.search`, a variable the `wordpressHooks` query never declares (so it was ignored and **every hook of the company** came back and was deleted, including other stores' hooks), and the query didn't request `options { pagination }`, so `Curl::complex()` stopped after the first 50 hooks. The filter now goes in `options.search` and the query asks for pagination.

**Rule:** because one hook now receives every Product operation (including `delete`, and the ones whose sync is switched off), nothing may be fetched before the operation's own setting is checked. Each `on*` handler checks `shouldSyncProduct()` / `shouldSyncStock()` and only then calls `fetchMoloniProduct()`; other operations fall through the `switch` and are acknowledged with no fetch and no log. Any `hooks` query filter must go in `options.search`, and the query must request `options { pagination }`.

**Not verified end to end** — no automated test/lint gate in this plugin (see `AGENTS.md › Verification`); this needs exercising in the local Docker WordPress: save automations with stock/product sync on, confirm exactly one `Product` hook exists (reinstall webhooks), then trigger a Moloni-side product delete and confirm no error is logged and no fetch occurs.
